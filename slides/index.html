J1.04
C'est quoi exactement DevOps ?

Pas un outil, pas un job. Une démarche.

Définition courte

DevOps est l'ensemble des pratiques culturelles, organisationnelles et techniques qui visent à raccourcir le cycle de livraison logicielle, tout en augmentant la qualité.

Ce n'est PAS :
• Un poste ("DevOps engineer" ≈ raccourci marketing)
• Un outil ("on fait du DevOps avec Jenkins")
• Du sysadmin renommé

Les 3 piliers

Culture

Responsabilité partagée Dev/Ops, ownership end-to-end, blameless.

Automatisation

CI/CD, IaC, tests, monitoring. Tout ce qui est répétitif est code.

Mesure

On pilote par les métriques (DORA), pas par l'opinion.

J1.05
Les 3 voies (Phoenix Project)

Le cadre conceptuel qui structure DevOps

1. Le flux

Du code vers la prod, sans accroc.

  • Petits batchs
  • Réduire le WIP
  • Automatiser le pipeline

Dev → Ops

2. Le feedback

De la prod vers le dev, vite.

  • Monitoring, alertes
  • Tests à toutes les étapes
  • Boucle courte

Ops → Dev

3. L'apprentissage continu

Expérimenter, accepter l'échec.

  • Post-mortems blameless
  • Game days, chaos eng
  • Partage des apprentissages

Culture

Une orga DevOps mature applique les trois. Beaucoup s'arrêtent à la voie 1 (automatisation), c'est insuffisant.

J1.07
Métriques DORA

Les 4 métriques qui mesurent vraiment la performance d'une équipe DevOps

Deployment Frequency

À quelle fréquence on déploie en prod ?

Elite : plusieurs fois/jour — Low : < 1/mois

Lead Time for Changes

Temps entre commit et déploiement en prod.

Elite : < 1h — Low : > 6 mois

MTTR

Mean Time To Recovery : temps de retour à la normale après incident.

Elite : < 1h — Low : > 1 semaine

Change Failure Rate

% de déploiements qui causent un incident.

Elite : 0–15 % — Low : > 30 %

Insight DORA : déployer plus souvent diminue le risque (petits batchs = petits failures faciles à fixer). Contre-intuitif mais validé chaque année.

J2.05
Branch protection rules

Settings → Branches → Add rule. C'est ce qui rend la PR obligatoire.

Règles essentielles

  • Require pull request avant merge
  • Required reviewers (1 ou 2 approvals)
  • Required status checks (CI verte)
  • Dismiss stale reviews au new push
  • No force-push sur main
  • Linear history (squash ou rebase)

Règles plus strictes (prod)

  • Require signed commits (GPG)
  • Require code owner review
  • Restrict who can push
  • Require deployment to succeed
  • Lock branch en pré-release
Sans branch protection, n'importe qui (vous compris à 23h un vendredi) peut bypass la PR avec git push origin main. Activez-la avant les premiers commits.
J2.06
Code review : qu'est-ce qu'on regarde ?

Ce qui compte

  • Correctness — la logique fait ce qu'elle dit
  • Tests — ils couvrent les cas, ils sont lisibles
  • Sécurité — secrets, injections, autorisations
  • Lisibilité — un junior comprendra dans 6 mois
  • Performance — uniquement si critique

Comment commenter

  • Soyez spécifique : "ligne 42, ce if peut crasher si X"
  • Distinguer must / nit : "must: ce bug" vs "nit: style"
  • Suggérer : utilisez les suggestions GitHub
  • Pas d'attaque : critiquer le code, pas la personne
Anti-patterns : review nitpick (uniquement style), review tardive (la veille du sprint), review-rubber-stamp (LGTM sans regarder), review ad hominem.

Détecté en…Coût relatifPourquoi
IDE (dev)1×Auto-correction, contexte chaud
CI (PR)10×Faut re-push, re-review, re-attendre

Premier workflow YAML

Le minimum vital pour avoir un job qui tourne

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
J3.05
Triggers — quand le workflow se déclenche
on:
  push:
    branches: [main, develop]
    paths: ['src/**', 'package.json']
  pull_request:
    types: [opened, synchronize, reopened]
  schedule:
    - cron: '0 3 * * *'        # tous les jours à 3h UTC
  workflow_dispatch:            # bouton manuel dans l'UI
    inputs:
      env:
        type: choice
        options: [staging, prod]
  workflow_call:                # réutilisable depuis d'autres workflows

Triggers usuels

  • push — sur main = build de référence
  • pull_request — checks bloquants
  • workflow_dispatch — déclenchement manuel

Filters utiles

  • branches: — restreindre à certaines branches
  • paths: — uniquement si fichiers modifiés
  • tags: — déclencher sur tag (release)

      - run: npm test

J3.07
Matrix builds

Tester sur plusieurs versions / OS sans dupliquer le job

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        node: [18, 20, 22]
        os: [ubuntu-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
      - run: npm ci
      - run: npm test
Effet : 3 versions × 2 OS = 6 jobs en parallèle. fail-fast: false permet de voir l'échec sur chaque combinaison plutôt que d'arrêter au premier rouge.
J3.08
Cache des dépendances

Le moyen le plus simple d'accélérer une CI

Méthode simple — setup-node

- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: 'npm'        # ← suffit

Caches automatiquement ~/.npm en se basant sur package-lock.json.

Cache générique — actions/cache

- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: deps-${{ hashFiles('package-lock.json') }}
    restore-keys: |
      deps-

Pour autre chose que Node (Maven, Gradle, Cargo, Go modules…).

Gain typique : npm ci passe de 60–90s à 5–15s. Sur 1000 runs/mois, c'est des heures de CI économisées.
J3.09
Marketplace & actions communautaires

Des milliers de briques prêtes — avec des règles d'hygiène

Actions officielles à connaître

  • actions/checkout — récupérer le code
  • actions/setup-node / setup-python / setup-java
  • actions/cache — caching
  • actions/upload-artifact — partager entre jobs
  • docker/build-push-action — image Docker

Hygiène

  • Pin par version : @v4 minimum
  • Pin par SHA en prod : @a1b2c3... (immuable)
  • Marketplace uniquement les "Verified creator" ou audités
  • Lire le code source avant d'adopter une action obscure
Faille typique : action tierce qui exfiltre vos secrets. Plusieurs incidents publics. Pinner par SHA empêche un mainteneur compromis de pousser un payload malveillant en sous-marin.

Cas d'usage : build Docker dans la CI

L'artefact qui va voyager jusqu'à la prod

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/setup-buildx-action@v3

      - uses: docker/build-push-action@v6
        with:
          context: .
          file: ./Dockerfile
          tags: devops-app:${{ github.sha }}
          load: true             # charge l'image dans le runner

      - name: Smoke test image
        run: |
          docker run -d --name app -p 3000:3000 devops-app:${{ github.sha }}
          sleep 3
          curl -fsSL http://localhost:3000/health
          docker stop app
Pourquoi Docker en CI : on teste exactement ce qui ira en prod. Plus de "ça marchait en CI mais pas en prod" parce que la CI utilisait Node 20 et la prod Node 18.
J3.13
Cas d'usage : push sur GHCR

GitHub Container Registry, gratuit, intégré, géré

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write           # ← requis pour push GHCR
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:latest
Tags multiples : :sha pour la traçabilité, :latest pour les utilisateurs. En prod, on ajoute aussi :v1.2.3 sur tag git.

Secrets — gestion

3 niveaux, des bonnes pratiques, et OIDC pour les pros

NiveauPortéeCas d'usage
RepoTous les workflows du repoAPI key spécifique à ce projet
OrganizationPlusieurs repos (avec restrictions)Token DockerHub partagé
EnvironmentWorkflow + environment précisCred de prod (avec approval)
steps:
  - run: deploy
    env:
      DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
      GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}    # auto-généré
À ne jamais faire : echo ${{ secrets.X }}, ni hardcoder dans le YAML, ni stocker dans des variables qui leakent dans les logs (URL, args CLI…).
OIDC (niveau pro) : pas de secret long-lived. GitHub signe un token court qui s'échange contre des creds AWS/GCP/Azure. À voir après ce cours.
J4.03
Environments & approvals

Modéliser staging / prod dans GitHub avec porte de validation

jobs:
  deploy-staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - run: ./deploy.sh staging
        env:
          DEPLOY_KEY: ${{ secrets.STAGING_KEY }}

  deploy-production:
    runs-on: ubuntu-latest
    needs: deploy-staging
    environment:
      name: production
      url: https://app.example.com
    steps:
      - run: ./deploy.sh prod
        env:
          DEPLOY_KEY: ${{ secrets.PROD_KEY }}

Settings de l'environment

  • Required reviewers — approval manuel
  • Wait timer — délai avant exécution
  • Deployment branches — uniquement main
  • Secrets isolés — pas accessibles aux autres envs

Bénéfices

  • Historique des déploiements lisible
  • Approval traçable (qui a validé quand)
  • Rollback rapide via redeploy précédent
J4.04
Cas d'usage : déploiement réel

Render / Fly.io / Railway, gratuit, déclenché au merge sur main

name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Trigger Render deploy
        run: |
          curl -fsSL -X POST \
            -H "Authorization: Bearer $RENDER_TOKEN" \
            "https://api.render.com/deploy/srv-xxxxx?key=$DEPLOY_HOOK"
        env:
          RENDER_TOKEN: ${{ secrets.RENDER_TOKEN }}
          DEPLOY_HOOK: ${{ secrets.RENDER_HOOK }}

      - name: Smoke test
        run: |
          for i in {1..30}; do
            curl -fsSL https://app.example.com/health && exit 0
            sleep 5
          done
          exit 1
Smoke test post-deploy : indispensable. Sinon le job est vert même si l'app est cassée. /health doit répondre 200 dans les X secondes après deploy.

J4.06
Sécurité supply chain

Les 4 réflexes pour ne pas être le prochain incident
